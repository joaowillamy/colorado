Projeto whatsapp/src · Node.js na Lambda

O código do atendente, por dentro

Foco no que não é óbvio: as camadas do evento, o lote do SQS, o lock no DynamoDB, o loop de tools do Converse e o que acontece quando algo quebra no meio. Os trechos de código abaixo são os arquivos reais de whatsapp/src.

01Mapa: quem faz o quê e quem importa quem

Analogia de cozinha de restaurante: o handler é o gerente do turno, o parseEvent abre os envelopes dos pedidos, o conversa é o caderno de comandas com cadeado, o atendente é o chef, o rag é o livro de receitas, as tools são os ajudantes que consultam o caixa, o guardrail é o fiscal da vigilância e o whatsapp é o garçom.

Clique num arquivo: em azul o que ele importa, em verde quem importa ele.

02Cold start: o que roda uma vez e o que roda sempre

O que está no escopo do módulo (fora do handler) roda só quando a Lambda cria um ambiente novo. Depois, o mesmo ambiente atende várias invocações e reaproveita esses objetos: clients do SDK com conexões HTTP abertas, o prompt.txt já lido, o config.

Consequência práticaMudar o prompt.txt sem deploy não muda nada: ele foi lido no cold start. E o deploy força ambientes novos, por isso o prompt novo vale já na próxima mensagem.

03parseEvent: a boneca russa

A mensagem do cliente chega embrulhada três vezes, e duas das camadas são strings JSON dentro de JSON. Por isso há três JSON.parse. Abra camada por camada usando o evento real de events/sqs-sns-mensagem.json.

Comece pela camada de fora: o record que o SQS entrega para a Lambda.

04handler: o lote do SQS e o batchItemFailures

A Lambda recebe até 5 records por vez. O handler achata as mensagens, ordena por timestamp (o SNS padrão não garante ordem) e processa uma por vez. No fim, devolve só os messageId do SQS que falharam: esses voltam para a fila, e o resto é apagado.

Monte o lote: escolha o que acontece com cada mensagem e rode. Telefone A e B. Os timestamps estão fora de ordem de propósito.

06O lock por telefone: duas Lambdas, uma conversa

O SQS padrão pode entregar duas mensagens do mesmo cliente para duas Lambdas ao mesmo tempo. Sem cuidado, as duas leem o histórico, respondem e gravam, e a última gravação apaga a outra (lost update). O carregarComLock resolve com um único UpdateItem condicional: pega o lock e lê o histórico na mesma operação atômica.

07Histórico: guardar, cortar e não quebrar o Converse

  
O histórico é o array messages do Converse, salvo como string JSON num atributo do item. Assim o DynamoDB não tenta mapear cada bloco aninhado (toolUse, toolResult) para os tipos dele. O aparar() mantém as últimas N mensagens, mas existe uma regra: o histórico tem de começar numa mensagem do usuário com texto. Começar num toolResult sem o toolUse que o pediu dá ValidationException.

08atendente: o loop de tools, turno a turno

  
A parte mais densa do projeto. Duas ideias guiam tudo: (1) o modelo não executa nada, ele só pede uma tool, e o seu código executa e devolve o resultado; (2) o que vai para o Bedrock é diferente do que fica salvo: o contexto do RAG entra só na requisição, por meio do comContexto().

09cachePoint: por que o nome do cliente vem depois

  
O cache do Claude guarda um prefixo da requisição. Tudo antes do cachePoint precisa ser idêntico entre chamadas para dar hit. Se o nome do cliente viesse antes, cada cliente teria um cache próprio, e o prompt de ~3 mil tokens seria regravado a cada pessoa nova.

Nos logs reais do seu atendente: {"input":4665,"cacheRead":3121,"cacheWrite":0}. O inputTokens do Converse não inclui os tokens lidos do cache: o total de entrada é 4665 + 3121.






  
10rag: buscar, filtrar por score, montar a mensagem

  
O buscar() chama o Retrieve do Knowledge Base e o filtro descarta trechos com score abaixo de SCORE_MINIMO. Mexa no corte e veja o custo. Os 5 primeiros scores são reais (pergunta "Quanto custa o ingresso VIP?"); os demais são ilustrativos.

11tools: o contrato toolUse → toolResult

  
O toolConfig descreve as tools com JSON Schema. A descrição é instrução para o modelo: a regra "consulte a matrícula antes de gerar link" está escrita lá, não no código. O código só faz o despacho pelo mapa EXECUTORES[name] e devolve o resultado com o mesmo toolUseId.

12guardrail: config condicional e o trace achatado

  
Truque 1. guardrailConfig é undefined quando GUARDRAIL_ID=off. O SDK omite campos undefined ao serializar, então a requisição sai sem guardrail e nenhum if é preciso no ConverseCommand.

  
Truque 2. O trace tem formatos diferentes de cada lado: inputAssessment é um objeto { idDoGuardrail: avaliação }, e outputAssessments é { idDoGuardrail: [avaliações] }. O Object.values(mapa).flat() normaliza os dois numa lista só.

  

  

  
Por que o log não leva o matchO trace traz o valor detectado em texto puro (o número do cartão, o e-mail). O achadosDoGuardrail loga só tipo e ação, de propósito. A documentação da AWS pede para tratar o trace como dado sensível.






  
13whatsapp: bytes, "+" e o "marcar como lida"

  

    

      
O campo message é um blob. Ele recebe o JSON da Cloud API da Meta, como bytes (TextEncoder). O End User Messaging repassa para a Meta.

      
O "+" que custou um debug. O webhook entrega o número sem +, e o SendWhatsAppMessage recusava com Invalid destination phone number or message Id. O normalizarTelefone resolve.

      
Marcar como lida é best effort. .catch(() => {}): os tracinhos azuis não valem um retry da mensagem inteira.

    

    

  

  
Por que o log() é tão pobre

  
Ele só aceita um nome de evento e alguns números. Telefone, e-mail e texto do cliente nunca entram, e por isso nem o input das tools é logado. É mais fácil não vazar do que limpar depois.
